# Issue #86 — физические денежные переводы: обнаружение общих слотов

Основа: PR #76 (`nika/economy-coin-conservation-20261118`).
Изменения только в отдельной ветке Issue #86. `main`, `SettlementAuthority`,
`DemandDeliveryCoordinator` и изменения MiniMax не затронуты.

## Причина

Две обёртки `Container` могут ссылаться на одни и те же физические слоты,
не будучи одним Java-объектом. Отдельные снимки до списания, затем запись
источника и назначения способны восстановить уже изъятые монеты. Сравнение
`source != target` недостаточно.

## Исправление

- `KingdomPhysicalSlotGuard`: сопоставление **реальных объектов-оснований
  по identity** (`IdentityHashMap`) и номеров физических слотов. Не доверяем
  `Object.equals()`. Запрещены любые пересечения, дубликаты внутри одной
  обёртки, неизвестная привязка слотов и пустые контейнеры.
- `KingdomContainerAccess`: `PhysicalSlotProvider` для строго известных
  источников. Поддержаны обычные `SimpleContainer`, ванильные Chest/
  TrappedChest/Barrel BlockEntity, составная обёртка двойного сундука.
  Произвольный `CompoundContainer`, модовый `IItemHandlerModifiable` и
  неизвестные сторонние обёртки **НЕ ДОПУСКАЮТСЯ** к `move/canMove` до
  появления проверенного сопоставления физических слотов. Это осознанная
  совместимость в пользу предотвращения дюпа.
- `KingdomBankVaultRooms.VaultContainer` передаёт исходную принадлежность
  каждого слота из реальных сундуков; сравнивается как с другим `VaultContainer`,
  так и с одним из входящих в него сундуков.
- `KingdomPhysicalCash.canMove/move`: проверка пересечений выполняется
  **до** создания планов/любого изменения. Количество **каждого** из трёх
  номиналов должно сохраниться. Невозможно слить «чистые» монеты с NBT-тегированными.
- `PhysicalCashCommitGate`: проверяет фактическую запись обоих инвентарей.
  При исключении `setItem` или тихом отказе записи пытается вернуть исходные
  снимки вместе с NBT, после чего проверяет каждый слот. Если откат не доказан,
  бросает `IllegalStateException` с требованием ручной сверки; не заявляет успех
  и не повторяет операцию.

## Автоматические тесты

- Два разных wrapper-объекта, один и тот же underlying storage.
- Пересечение одной половины составного сундука; симметрия и непересечение.
- Повторение номера слота, неопределённая физическая принадлежность,
  равные `equals()` при разных Java-объектах.
- Успешная передача, повторный перевод, `setItem` бросает до/после
  изменения, частичная запись, тихий отказ, недоказанный откат.
- Контрактный тест подключения к реальным `KingdomPhysicalCash`,
  `KingdomContainerAccess`, `KingdomBankVaultRooms`; запрет неявного
  размена и объединения tagged coins.

## Что необходимо проверить на Forge 47.3.0/TFC/Create до слияния

1. На копии мира: сундук с 64+36 медными; создать 2 обёртки одного
   основания; `move(A,B,100)` должен вернуть false, осталось ровно 100.
2. Две обёртки двойного сундука, включая перекрытие только одной половины:
   всегда отказ без изменений.
3. Два непересекающихся реальных сундука: переносить только реальное
   количество каждого номинала, без изменения NBT/других предметов.
4. Полный target, частично свободный target, tagged copper/silver/gold,
   контейнер с исключением `setItem`, тихий отказ `setItem`.
5. Сохранить/перезапустить сервер и проверить повторную операцию,
   физические остатки и неповреждённый мир.
6. Отдельно: TFC/modded-контейнеры могут временно отказаться от переводов
   (неизвестная identity), пока их underlying storage не получит
   проверенный адаптер. Нельзя обходить fail-closed условие.

### Ограничение

Это защита **в пределах одного тика сервера**, не журнал транзакций между
разными файлами сохранения Minecraft. Crash-atomicity банковских счетов —
отдельный Issue #78/PR #89; его код здесь не дублируется.
Фактический игровой тест и аварийное выключение должны быть выполнены
на сервере Forge, чтобы подтвердить физический результат, не только JUnit.
