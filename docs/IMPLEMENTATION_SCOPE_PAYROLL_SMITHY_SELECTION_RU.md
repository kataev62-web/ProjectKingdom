# Обновление: выделение зданий, зарплатный счёт и производство кузницы

Статус документа: текущий план реализации и приёмки ветки `feature/payroll-smithy-production-selection`.
Платформа: Minecraft 1.20.1 / Forge 47.3.0 / Java 17 / TerraFirmaCraft.

## 1. Выделение здания — новый UX

Управление состоит из трёх физических действий:

1. Shift + пустая основная рука + ЛКМ по первому углу пола.
2. Shift + пустая основная рука + ЛКМ по противоположному углу пола на той же высоте.
3. Shift + пустая основная рука + ПКМ по верхней точке; высота берётся из Y выбранного блока.

Координаты берутся только из серверных событий взаимодействия. Клиент не может прислать произвольный объём. Сохраняются TTL сессии, проверка измерения, расстояния, чанков, владения участком, пересечения комнат и минимальный габарит 2×2×3. После неуспешной проверки горизонтальная часть остаётся выбранной, игрок повторяет только вертикальный шаг.

Проверить отдельно:
- LMB не ломает блоки и не запускает чужие меню во время сессии;
- off-hand не дублирует действие;
- вертикальная точка ниже пола отклоняется;
- прямоугольник обязан включать ядро предприятия;
- визуальный контур обновляется на всех трёх шагах и очищается после завершения/отмены.

## 2. Зарплатный счёт предприятия\n\n### Уже внесено в ветку\n- Добавлена отдельная роль физического хранилища `SALARY_STORAGE`, не смешанная с кассой предприятия.\n- В меню финансов предприятия добавлены привязка зарплатного сейфа и пополнение на 100 медных.\n- Баланс показывается по фактическим монетам в физическом контейнере; отдельная виртуальная сумма не создаётся.\n- Автоматическая выдача NPC теперь списывает монеты из зарплатного сейфа, проверяет реального загруженного NPC и вместимость его личного кошелька.\n- Работодатель может вручную выплатить долг NPC из его меню, только рядом с загруженным зарплатным сейфом и самим NPC.\n- Маршрут NPC направляет его к зарплатному сейфу для получения начисленного долга; после увольнения сохранённый долг также остаётся доступен к погашению.\n\nОстаётся: расширить журнал выплат, добавить удобную настройку ставок и полный список работников в меню предприятия; проверить реальные маршруты и выплаты в игре.

Не смешивать зарплатные средства с оборотной кассой, личным балансом владельца, городской казной или legacy-резервом NPC.

Требуемая модель:
- отдельный сохраняемый баланс salaryAccount по UUID предприятия;
- пополнение только реальными монетами, проверенными по номиналу и физически перемещёнными в защищённое хранилище зарплатного счёта;
- при пополнении увеличивать бухгалтерский баланс только на фактически перемещённую стоимость;
- выплаты NPC списывают только salaryAccount и создают/перемещают реальные монеты в сохраняемый кошелёк NPC;
- никаких виртуальных денег, удалённой выплаты из обычной кассы или дублирования монет;
- журнал операций: пополнение, начисление, выплата, частичная выплата, отказ из-за нехватки средств;
- миграция старых сохранений: старые кассы и долги не переносить автоматически в зарплатный счёт.

Меню предприятия:
- вкладка «Зарплата»;
- баланс зарплатного счёта;
- пополнение физическими монетами;
- ставка каждого сотрудника и начисленный долг;
- список сотрудников;
- история последних операций.

Меню NPC:
- ставка в день;
- начислено / выплачено / долг;
- кнопка работодателя «Выплатить зарплату» для полной или доступной частичной выплаты;
- отдельный статус автоматического получения зарплаты самим NPC.

Поведение:
- NPC ежедневно подходит к зарплатному пункту предприятия и забирает причитающуюся сумму, если счёт пополнен;
- маршрут не должен телепортировать NPC или загружать чанки;
- если счёт пуст, долг сохраняется; после утверждённого порога неоплаченной работы NPC приостанавливает работу;
- ручная выплата из меню NPC доступна только владельцу/уполномоченному менеджеру, рядом с NPC и с серверной проверкой предприятия;
- ручная выплата не может обойти долг, договор или лимит вместимости кошелька;
- после погашения долга работа возобновляется только при действующем договоре.

## 3. Производство кузницы\n\n### Уже внесено в ветку\n- Каталог выбора рецепта кузнеца собирается из всех реальных предметов в привязанном сырьевом складе.\n- В список попадают только рецепты TFC, допустимые для фактического уровня установленной наковальни.\n- Список уникален и сортируется по ID рецепта; выбор сохраняется в данных NPC.\n\nОстаётся: производственная очередь с количеством изделий, приоритетом и состояниями заказов; отдельный интерфейс категорий (инструменты, оружие, броня, металлургические заготовки); сохранение незавершённого заказа и прогресса после перезапуска; обработка нехватки сырья/топлива/места.

Не хардкодить каталог конечным списком предметов. Строить его из зарегистрированных рецептов установленной версии TFC и доступных наковален/металлов.

Категории интерфейса:
- инструменты: кирки, лопаты, мотыги, топоры, ножи, пилы, молоты, зубила, косы, пропики и прочие реальные предметы TFC;
- оружие: мечи, копья/дротики, щиты и прочее поддерживаемое оружие;
- броня и защитное снаряжение;
- металлургия: слитки, двойные слитки, листы, двойные листы, заготовки и прочие рецепты TFC;
- детали и компоненты, если они реально производимы через доступные механики TFC;
- отдельные литейные изделия, если рецепт и фактический процесс доступны в TFC.

Производственный заказ:
- изделие, металл/материал, качество (если оно задаётся TFC), количество, приоритет;
- проверка сырья, топлива, формы/наковальни, уровня наковальни и необходимых инструментов;
- очередь заказов с состояниями: ожидает сырьё, готов к работе, в процессе, ожидает место на складе, готов, ошибка;
- расходовать только фактические предметы из привязанного склада;
- не выдавать готовое изделие через прямое создание ItemStack вместо выполнения реального TFC рецепта;
- сохранять незавершённый заказ и этап процесса после перезапуска;
- готовую продукцию класть в привязанный склад; если он полон — удерживать предмет в безопасном реальном инвентаре станка и показывать причину;
- сообщения над NPC: что требуется, что закончилось, какой заказ выполняется.

Сначала поддержать нативный TFC charcoal forge + anvil-процесс. Если рецепт не исполним через текущий адаптер (например, требует ручных действий/несовместимого станка), показать его как недоступный с объяснением, а не обещать производство.

## 4. Тесты и критерии приёмки

### Выделение
Unit/regression tests на преобразование двух горизонтальных точек и высоты в корректные min/max; границы размеров; одинаковую высоту пола; сохранение сессии при ошибке; проверку владельца и пересечений.

### Зарплата
Тесты сохранения/загрузки зарплатного счёта, миграции, точного физического пополнения, частичной выплаты, полного погашения, недостатка средств, повторного клика/дедупликации, увольнения с долгом, перезапуска сервера, переполненного кошелька и запрета двойного расхода.

### Кузница
Тесты каталога по реальным зарегистрированным рецептам, фильтрации по наковальне/металлу, очереди, нехватки топлива/сырья, полного склада, рестарта, отсутствия дублирования предметов и корректной обработки неподдерживаемого рецепта.

Сборка Gradle и автоматические тесты обязательны. Затем — ручная проверка на выделенном клиенте/сервере с фактической версией TFC. До этих проверок нельзя маркировать функциональность как полностью готовую.
