# Авторитет расчётов (SettlementAuthority) — статус и границы

**Дата:** 18.11.2026 · **Ветка:** `minimax/kingdom-server-authority-20261118` · **Ветвление от:** `origin/main` (`407f68f3`)

## Что решено

До этого раунда сервер умел только **не применять** спорную операцию: `DemandDurableSettlementGate`
и `TradeWriteAheadJournal` оставляли метку `PREPARED` и требовали ручной сверки оператора
(`/knpc supply-recovery resolve`). Довести до конца решённую операцию после падения сервера
было нельзя, потому что не было ни единого авторитетного журнала, ни идемпотентной проекции,
ни проверки «применено или ещё нет».

Добавлен `SettlementAuthority` — серверный компонент, который:

1. **Принимает решение до изменения мира.** Запись `PREPARED` содержит план доставки и
   ожидаемое количество каждой затронутой пары (контейнер, предмет). Запись `COMMITTED`
   фиксирует решение. Только после этого трогаются контейнеры.
2. **Проецирует идемпотентно.** Каждая затронутая пара (контейнер, предмет) хранит
   ожидаемое количество «до» и «после». После перезапуска авторитет сравнивает фактическое
   количество с ожидаемым и доделывает ровно недостающий шаг, а не повторяет выполненный.
3. **Не угадывает.** Если фактическое количество не совпадает ни с «до», ни с «после»,
   доставка карантинируется для оператора: ни товар, ни деньги не двигаются.
4. **Не применяет нерешённое.** Доставка, для которой есть `PREPARED`, но нет `COMMITTED`,
   никогда не применяется автоматически: решение не было долговечным, состояние мира
   неизвестно. Такая доставка блокирует и остальные.
5. **Восстанавливается повторяемо.** Повторный проход восстановления ничего не меняет.

Формат журнала: `SettlementJournal` — append-only строки `KIND|payload|crc32`, каждая запись
принудительно сбрасывается на диск (`FileChannel.force`) до возврата из метода. Повреждённый
хвост журнала обнаруживается по контрольной сумме и **сообщается**, а не игнорируется.

## Протокол состояний

| Запись | Смысл | Что происходит при падении |
|---|---|---|
| `PREPARED` | план и ожидаемые количества | доставка карантинируется, контейнеры не тронуты |
| `COMMITTED` | решение принято | восстановление доделывает проекцию |
| `RECEIPT` | проекция выполнена и проверена | доставка завершена |
| `REJECTED` | доставка отклонена (не хватило товара, места или монет) | состояние мира не менялось |
| `QUARANTINED` | нужен оператор | доставка не применяется, следующие ждут |

Оператор закрывает карантин явно: `CONFIRMED_APPLIED` (доставка в мире есть) или
`CONFIRMED_NOT_APPLIED` (доставки не было). Оба решения записываются в журнал.

## Что проверено фактически

Стенд `validation/server_authority_harness/run.sh` — чистая Java, без Minecraft и без сети.
Проверено: 7 сценариев, 11 точек падения.

| Проверка | Результат |
|---|---|
| Нормальная доставка: товар в склад, оплата в кошелёк | PASS |
| Повтор той же доставки (тот же id) | PASS — `DUPLICATE`, состояние не меняется |
| Падение на 11 границах записи (до/после записи, после сброса на диск, после товаров, после монет, перед квитанцией) | PASS — ни один товар и ни одна монета не созданы и не потеряны, ни одна доставка не применена дважды |
| Восстановление после падения | PASS — нерешённая доставка карантинируется, решённая доделывается ровно один раз |
| Повторное восстановление | PASS — идемпотентно, состояние не меняется |
| Чужое вмешательство в контейнер (количество не совпало) | PASS — карантин `inconsistent_state`, деньги не двинулись |
| Отказ поставки (нет товара, нет места, нет монет) | PASS — состояние не меняется, повтор остаётся отказом |
| Два параллельных покупателя | PASS — каждая доставка применена ровно один раз |
| Разрешение оператором | PASS — после решения очередь продолжается |
| Повреждённый журнал | PASS — повреждение сообщается, доставки карантинируются, вслепую не применяются |

Команда: `bash validation/server_authority_harness/run.sh`

## Границы — важно

- **Это не атомарный коммит Minecraft.** Журнал фиксирует решение и прогресс, но запись
  чанка и `SavedData` — независимые операции. `sync-chunk-writes=true` в конфигурации
  выделенного сервера нужен для совместной долговечности.
- **Проверка по количеству не видит подмену.** Если контейнер изменился так, что количество
  совпало, авторитет применит доставку. Это ограничение проверки количества, а не журнала.
- **Авторитет не владеет предметами и деньгами.** Он двигает дельты между переданными
  контейнерами.
- **Forge-сборка в этой среде не выполнялась.** `SettlementMinecraftPorts` (адаптер к
  `net.minecraft.world.Container`) проверен только компиляцией против минимальных заглушек
  Minecraft и по образцу существующего `DemandMinecraftContainerPorts`. Полную сборку
  (`./gradlew build`) и игровой тест на настоящем сервере нужно прогнать отдельно.
- **Авторитет не подключён к командам бота.** Ни `DemandDeliveryCoordinator`, ни
  `/knpc supply-recovery` в этом раунде не переведены на новый протокол: это отдельная
  задача, потому что она затрагивает файлы других потоков.

## Следующий шаг

1. Перевести `DemandDeliveryCoordinator` и `/knpc supply-recovery` на `SettlementAuthority`.
2. Прогнать `./gradlew build` и тесты на настоящем выделенном сервере Forge 47.3.0.
3. Прогнать игровой сценарий «перезапуск сервера посреди доставки» на копии мира.
